AI literacy primer for staff: how it is being made (draft for review)

This page describes the process, not the content. The primer is a plain-language guide for SCII staff, built to help anyone, whatever their subject or starting point, to understand the main ideas, judge claims, tools and sources for themselves, see where their own subject differs, treat contested ideas as questions to argue with, tell what is stable from what is changing, and keep talking about it as the debate moves. It is a draft for review, not approved, and not for circulation.

Process steps

  1. Agree the intent. Check with the SCII Gen AI group what "baseline" should mean, so the work is right first time.
  2. Gather and check sources. Find sources, test definitions, and record for each one what type it is, whose interest it serves, and how far to lean on it.
  3. Map the current dialogue. For each subject area, identify what is being said now: the live debates, how practitioners and students are responding, and who is speaking. Note where views differ, and date each snapshot.
  4. Draft in layers. Write in plain language, from basic ideas to current debates, with numbered references so every claim can be traced.
  5. Develop with each subject area. Subject leads shape how the primer speaks to their discipline, since each brings its own opportunities and challenges.
  6. Review by the group. The group reviews the draft and says what to cut, change or add.
  7. Revise and set review dates. Update the draft, and put a review date and a named owner on each page, because some topics date quickly.
  8. Check accessibility. Build and check to WCAG AA, with a tagged PDF as the accessible fallback.
  9. Approve and hand over. Agree approval, a home on SHU infrastructure, and hand-off to the board.
  10. Keep the dialogue going. The primer is not finished at hand-over. Each subject area keeps an ongoing conversation (regular check-ins with subject leads, staff and students) about what has changed, and what it learns feeds back into the next review.

Recipe: recreating this process

Anyone in the group, whatever their role, can pick this up and run it again for a new topic, a new subject area or the next review. It does not depend on one person.

You will need

  • A named owner and a few reviewers, including at least one subject lead.
  • A shared folder, with one plain-text source file as the master and a log of decisions.
  • A source register: one line per source, giving its type, whose interest it serves, and how far to lean on it.
  • A fixed review date and a way to run the accessibility check.

Method

  1. Write down the purpose in a few sentences: who it is for, and what they should be able to do afterwards.
  2. List the questions the audience needs answered, not the answers.
  3. For each question, find sources and add each one to the register before using it.
  4. Map the current dialogue: what is being said now, by whom, and where views differ. Date it.
  5. Draft in plain language, layered from basic to advanced, with numbered references.
  6. Ask the relevant subject lead to correct and extend their part.
  7. Run a review round, with a set window and clear questions for reviewers.
  8. Revise, log what was decided and why, and set the next review date.
  9. Build the outputs from the one source (web and printable), then run the accessibility check.
  10. Hand over: confirm the owner, where the files live and when the next conversation happens.

Check it worked

  • Someone who did not write it can follow the log and reproduce the outputs from the source.
  • Every claim traces to a source in the register.
  • The next review date and owner are on every page.
